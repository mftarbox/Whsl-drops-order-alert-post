# Design spec: Wholesale WIP "Dropped" → NetSuite Order Rework Alert

Full history of decisions and platform findings from building this automation (2026-08-07 build session). Kept here as the record of *why* the code looks the way it does.

## Goal

When a style's Planning Indicator moves to Dropped on Wholesale WIP, find every not-yet-fulfilled NetSuite wholesale order with a line item matching that style's Master SKU, and create/update a Monday pulse per affected order on Wholesale Sales L10 → Wholesale Order Board.

## Decisions

1. Trigger read: WIP2027's real `status_1__1` field, not Wholesale WIP's mirror column - monday.com's API cannot read or filter "lookup" (mirror) column types at all (confirmed directly: `"This column type is not supported yet in the API"`). Wholesale WIP's `board_relation_mm5z9qmh` link is used to scope WIP2027's 1,776 items down to the ~20 wholesale-relevant ones.
2. Delivery: scheduled GitHub Actions polling, not a live Monday webhook.
3. Cadence: once daily at 8:00 PM Mountain time. GitHub Actions cron is fixed UTC and doesn't observe daylight saving, so the workflow schedules two cron ticks (covering both MST and MDT) and the script itself checks the current Mountain hour, no-opping on whichever tick isn't actually 8pm right now.
4. Wholesale identifier: NetSuite `cseg_order_class` (a **custom** "Order Class" segment field, distinct from the standard NetSuite `class` field, which also exists on transactions but isn't the one used) = internal ID 7, confirmed via `BUILTIN.DF(cseg_order_class)` → "Wholesale".
5. "Not fulfilled" (header): order status B (Pending Fulfillment), D (Partially Fulfilled), or E (Pending Billing/Partially Fulfilled).
6. "Not fulfilled" (line level): required - a partially-fulfilled order should only trigger if the *specific line* matching the dropped SKU still has remaining quantity. `quantityFulfilled` isn't exposed to NetSuite's Search/SuiteQL API at all, so remaining quantity is computed via NetSuite's standard `PreviousTransactionLineLink` table (`linktype = 'ShipRcpt'`) joined back to the shipped Item Fulfillment lines, summed and compared to `quantity` (which is stored negative for outbound transactions like Sales Orders - use `ABS()`).
7. Destination: Wholesale Sales L10 (board 3552781534), group "Wholesale Order Board" (`new_group_mkn8x1ye`).
8. Idempotency: checkbox column "Rework Alert Sent" (`boolean_mm60zwwz`) added to Wholesale WIP - only unprocessed + Dropped items are considered.
9. No backfill - only styles that move to Dropped after this automation went live. (As of go-live, none of the 20 wholesale-relevant styles were sitting at Dropped, so no manual pre-check of the new checkbox was needed.)
10. Pulse name: `"{Order #} has drops - {Customer Name}"`.
11. Pulse `person`: order's `salesrep` (an employee) → if that employee's `custentity_shin_inside_rep` is true, use the salesrep; if false, use that same employee's `custentity_assigned_inside_rep` instead. Both fields live on the **Employee** record, not the Customer record (an early assumption that was wrong - customer-record fetches for these field IDs silently returned nothing rather than erroring, which is what surfaced the mistake). The resolved employee is matched to a Monday user by email (`users(emails: [...])`).
12. All other pulse columns (Priority, Status, Due Date, Notes, External ID) intentionally left blank for now.
13. An order that later matches a second dropped SKU gets an update/comment appended to its existing pulse rather than a duplicate pulse, tracked via `state/state.json` (order # → Monday pulse ID), committed back to the repo by the workflow each run.
14. No additional notification channel - the Monday pulse itself is sufficient.
15. Before appending an update to a previously-created pulse (via `state/state.json`), the script checks that pulse's current `state` on monday (`active`, `archived`, `deleted`, or not found at all for a fully-deleted item). Only `active` pulses get the append. If the pulse was archived, trashed/deleted, or no longer exists, the script creates a brand-new pulse instead and overwrites the order's entry in `state/state.json` to point to the new pulse ID (added 2026-08-08, per Shelly's direction after the Monday OAuth app rebuild).
16. Pulse comment: every pulse - both on first creation and on every later append - gets a comment containing the NetSuite sales order link, customer name, order number, a "Master SKU | Shopify Title" line per distinct dropped style matched on that order, and a "Variant Size | Qty Ordered" line per matched order line, sorted by `custitem42` (position, ascending; items missing a position sort last). Field sources confirmed with Shelly directly against a real item record: Shopify title = `custitem_nu_sales_title`, variant size = `custitem35`. NetSuite order link format confirmed from Shelly's own browser: `https://{NETSUITE_ACCOUNT_ID}.app.netsuite.com/app/accounting/transactions/salesord.nl?id={so_internal_id}` (the classic UI domain - different from the SuiteTalk REST domain used for API calls). Scope is "this run's drops only," not a full cumulative history - if two styles drop in the same run and both match the same order, they're combined into one comment; drops from earlier runs already appended their own separate comments and aren't re-listed. (This was briefly reverted on 2026-08-07/08 while a missing `updates:write` OAuth scope on the Monday app was tracked down - see the OAuth troubleshooting note in "Platform quirks" below - and reinstated once the app was rebuilt with the correct scope and confirmed working live on 2026-08-08.)

17. **Add to NuOrder -> Remove** (built 2026-08-08): unconditional side effect of a style dropping, fires at the very start of that item's processing loop - before order matching, before the Wholesale L10 / Sales Ops L10 pulses. Sets Wholesale WIP's `color_mm5zz20q` ("Add to NuOrder", a status column with labels Add/Remove/Synced) to "Remove". Wrapped in its own try/catch so a failure here doesn't block anything else for that item. The existing Celigo integration automatically unchecks NetSuite's "NuOrder Active" checkbox (NOT "NuOrder Sync") on the matching item(s) once this flips - nothing built for that half, it already happens on its own. "Rework Alert Sent" semantics are unchanged - Shelly explicitly rejected making it conditional on every other step succeeding, due to duplicate-comment risk on partial retries.

18. **Sales Ops L10 "close items" CSV pulse** (built 2026-08-08): same Dropped trigger, same run, reuses the exact rows already fetched by the Wholesale L10 order-matching query (no second SuiteQL query) - one CSV per dropped *style* (not per order), aggregating every matched line across every matched order for that style. Columns (as of 2026-08-10, see 18a/18b - Amount/Item were added and then dropped again same day): **Internal ID** (`so.id`), **Closed** (always literal `TRUE`), **Line ID** (the simple `line` sequence number - see 18b for why NOT `lineUniqueKey`). `line` comes from `getSalesOrderLines()` in `lib/netsuite.js`, a `GET /record/v1/salesorder/{id}?expandSubResources=true` call - confirmed live against a real order (MSO-4061, internal id 62186518) that this returns `item.items[]`, each entry shaped like `{ item: { id, refName }, line, lineUniqueKey, isClosed, amount, ... }`. Since the SuiteQL matching query can return multiple rows for the same item on one order (e.g. the same SKU ordered on two separate lines), matched lines are handed out from a per-order, per-item-id queue (`resolveOrderLineDetails`) so two SuiteQL rows can never both grab the same underlying NetSuite line. Destination: **Sales Ops L10** (7017226460), group **ToDo** (`new_group72329__1`), pulse named `"{Master SKU} dropped - Close items on Sales Orders"`, Priority Level (`status_1_mkm2z4qr`) = **"High Priority"**. One comment contains both a hyperlink (display text **"Whsl Close Sales Order Items"**) to the Close Sales Order Items CSV Import mapping (`https://4775967.app.netsuite.com/app/setup/assistants/nsimport/importassistant.nl?recid=311&new=T`) and the CSV attached directly to that comment via `add_file_to_update` (Sales Ops L10 has no Files-type column, confirmed fine with Shelly).

18a. **Close items CSV: Closed always TRUE; Amount/Item added, then dropped again** (2026-08-10): Shelly first asked for `Closed` to always write literal `TRUE` (every line on this CSV is one being closed, regardless of its actual `isClosed` value in NetSuite - all-caps per her explicit choice over lowercase `true`) - that stuck. She also asked for an `Amount` column (raw NetSuite line `amount`, as-is) and an `Item` column (the line's `item.refName`, already `Parent : child-size`) to be added for Sales Ops visibility; both were informational only, since the saved import (recid=311) only ever mapped Internal ID/Closed/Line ID to real NetSuite fields. After previewing that 5-column version, Shelly asked to drop Amount and Item again - final column order is back to **Internal ID, Closed, Line ID** (3 columns, matching decision 18's current state). `buildCloseItemsCsv()` and the `csvRows.push()` call site in `run.js` were trimmed accordingly; `getSalesOrderLines()` still returns `amount`/`itemRefName` (cheap off the same fetch) but they're unused for now.

18b. **Line ID: resolved to the simple `line` sequence number, NOT lineUniqueKey** (2026-08-10): Preview CSVs were built and approved against a real order (WSO-DropTEST, internal id 62270327) using `lineUniqueKey` for "Line ID", per an earlier verbal confirmation from Shelly (recorded in decision 18's original text) that "Line ID" meant lineUniqueKey - a persistent, position-independent identifier that stays valid even if the order is resaved or lines are reordered, which is Shelly's hard requirement for this feature. When Shelly manually tested one real line (lineUniqueKey 251186457) via the saved "Close Sales Order Items" import, it failed with "The record has been deleted since you retrieved it." Screenshots of the import's Field Mapping step showed "Line ID" was actually bound to NetSuite's `line` field (the simple, position-dependent sequence number), not `lineuniquekey` - sending a lineUniqueKey value like `251186457` there made NetSuite try to resolve it as line position 251186457 on a much-shorter order, which doesn't exist. Research (Oracle's own CSV import docs, and independent NetSuite consultant write-ups) confirmed this is a real platform gap, not a configuration mistake: the classic CSV Import Assistant's transaction-line matching only supports the positional `line` field ("Order Line"/"Line Id") - `lineuniquekey` is a newer field exposed via NetSuite's REST/SuiteScript APIs but was never added to the classic Import Assistant's mappable-field list for transaction sublists, confirmed by Shelly finding no lineuniquekey option in the recid=311 mapping dropdown. Shelly then manually re-tested using the correct `line` value (2, matching lineUniqueKey 251186457's actual current position) via the exact 3-field mapping shown in her screenshot (Internal ID -> `id`, Closed -> `isclosed`, Line ID -> `line`) and confirmed it works - a follow-up live fetch of order 62270327 shows that line now has `isClosed: true`. **Decision: use `line`, not `lineUniqueKey`, for the CSV's "Line ID" column** - `buildCloseItemsCsv()` and `getSalesOrderLines()` in `lib/netsuite.js` were updated accordingly. **Known limitation, accepted by Shelly**: since `line` is position-dependent, this CSV's Line ID values are only valid as of the moment the CSV was generated - if the order is resaved with lines reordered/added/removed before the CSV is imported, the wrong line could get closed. Mitigate by importing promptly after the CSV is posted to Sales Ops L10.

19. **NuOrder imagery export to Dropbox** (built 2026-08-08): a wholly independent trigger from Dropped - runs every time this script runs (same 8pm Mountain cadence), gated on Wholesale WIP's real `color_mm5zz20q` ("Add to NuOrder") = "Add" and WIP2027's own `boolean_mm61mp3r` ("NuOrder Images Exported") checkbox being unchecked. This idempotency-checkbox design deliberately replaces needing to track "did this just change to Add" against a prior poll - it naturally covers both "newly changed to Add" and "new item created already at Add," and the WIP2027-side "New Pic!" button re-triggers a re-export simply by unchecking the same box. **Monday-side setup for this feature (columns + automation) lives on WIP2027 (18388071004), not Wholesale WIP** - see the "Option B" note below for why. Images come from WIP2027's real `files2__1` field (Wholesale WIP's own Image column is also an unreadable mirror, same limitation as Planning Indicator). Export filename = `{Master SKU}-0{sequence}.{ext}` (e.g. `10176-3232-01.png`) where sequence is a literal single digit (1-5) in the order files appear in the column (upload order) - confirmed with Shelly against real WIP2027 filenames, which do NOT already match this convention and must be renamed on export, not passed through. Binary content/type/size pass through completely untouched. Upload is to Dropbox path `/NuOrder Imagery/{filename}` in **overwrite** mode (same filename replaces in place, no auto-renamed duplicate).

20a. **Add to NuOrder -> "Update NetSuite" after imagery export** (built 2026-08-08): added after the base feature 3 build and confirmed live-working. After each item's export attempt in `processNuOrderImageExports` - success or failure - Wholesale WIP's `color_mm5zz20q` gets set to its **"Update NetSuite"** label (confirmed via `get_board_info` this is a real, existing label on that column, not a typo for "Synced" - the column's own Monday description says it "drives the Celigo sync that checks/unchecks the NuOrder Active / NuORDER Sync boxes on the matching NetSuite item(s)"). Shelly explicitly chose "fire regardless" over "only on full success" when asked - implemented via a `finally` block wrapped in its own independent try/catch (so a failure flipping the status gets its own Slack alert rather than masking, or being masked by, the export result). Once flipped away from "Add," the item naturally drops out of this feature's `targets` filter on the next run, so it won't re-fire repeatedly.

20. **Slack error alerts** (built 2026-08-08): a Slack Incoming Webhook (`SLACK_ALERTS_WEBHOOK_URL`, no bot/OAuth scopes needed) posts to **#whsl_ops_workflow_alerts** (C0ARSBBPGP7) on **both** fatal (uncaught, whole-run-ending, via the top-level `main().catch()`) and per-item/per-order errors that are otherwise just logged and swallowed (NetSuite query failures, item/customer detail lookups, pulse creation failures, the NuOrder flag flip, the imagery export, etc.) - confirmed by Shelly: alert on both tiers. `sendSlackAlert()` in `lib/slack.js` is deliberately built to never throw, so a Slack outage or bad webhook URL can't itself take down the real automation run. A related ask - manual workflow triggers *from* Slack (full-run and imagery-only) - was scoped in the same conversation but explicitly paused by Shelly as more work than she wants to take on right now; see project memory for that scope if it gets picked back up later.

21. **Trigger Celigo's native "Monday to NetSuite" sync flow in-workflow instead of on its own separate schedule** (built 2026-08-10): Shelly's existing Celigo flow watches for "Add to NuOrder" changes (both the "Remove" label from feature 1 and the "Update NetSuite" label from 20a) and syncs the NuOrder Active/Sync checkboxes to NetSuite - previously purely on its own native Celigo schedule, independent of this script. Shelly asked to trigger that flow from within this run instead, fully replacing its separate schedule. **Timing decision**: within one run, "Add to NuOrder" can change in two places - the Update NetSuite flip (inside `processNuOrderImageExports`, runs first) and the Remove flip (inside the per-dropped-item loop, runs later). Rather than call Celigo inline at each of those two spots (which could fire the API multiple times per run and would need two separate call sites), Shelly chose a single call once at the very end of the run (`finishRun()`), after every possible "Add to NuOrder" change for that run has already happened - including on the early-exit path where there were no drop candidates, since feature 3's flips still happen before that check. Fires unconditionally every run (not gated on whether anything actually changed - Shelly's call), and never throws past its own try/catch - a Celigo failure logs + Slack-alerts like every other non-fatal error path here, but doesn't affect the run's exit code (Shelly's call, matching this script's existing conventions).
    - **Mechanism**: Celigo's `POST https://api.integrator.io/v1/flows/{flowId}/run` runs a flow on-demand independent of its native schedule - confirmed via Celigo's own API docs that a flow doesn't need reconfiguring to support this (the schedule and on-demand-run capability are separate settings).
    - **Flow ID**: `6a7520cb8d2dd2212253f91d` (from the flow's URL in integrator.io: `https://integrator.io/integrations/66f5896552a1b5dd437da348/flowBuilder/6a7520cb8d2dd2212253f91d`), hardcoded as `CELIGO_MONDAY_TO_NETSUITE_FLOW_ID` in `run.js` (not a secret - just an identifier, same convention as the Monday board/column IDs elsewhere in this file).
    - **Credential quirk worth remembering**: Shelly's Celigo login has access via a **shared account**, not an owned one. Celigo's UI rejected setting *any* access-scope field on a generated token - including just toggling "Full access" on - with the error "Scope fields cannot be set on shared account tokens. Permissions are inherited from the account share." The fix: generate the token with only name/description/expiration set and no scope fields touched at all (not even an empty selection) - permissions are then inherited automatically from whatever the account share already grants. If this token ever needs broader/different access than the account share provides, that has to be changed by whoever owns/administers the parent Celigo account - not fixable from Shelly's own token settings.
    - Implemented in `lib/celigo.js` (`runCeligoFlow(flowId)`), following the same minimal-fetch-client pattern as `lib/dropbox.js`/`lib/monday.js`. Token lives in the `CELIGO_API_TOKEN` GitHub secret.
    - **Bug found and fixed (2026-08-21) before `CELIGO_API_TOKEN` was even added**: the first manual test run crashed the *entire* script (not just the Celigo step) with `Missing required environment variable: CELIGO_API_TOKEN`, because `lib/celigo.js` originally checked for the token at module load time (`const API_TOKEN = requireEnv(...)` at the top of the file) - same pattern as `lib/monday.js`/`lib/dropbox.js`, which is correct for THOSE since they're hard requirements for the whole script, but wrong here since Celigo failures are supposed to log + Slack-alert without affecting anything else (per the original design in this same decision). Fixed by moving the `requireEnv('CELIGO_API_TOKEN')` call inside `runCeligoFlow()` itself, so it only throws when the function is actually called - which `finishRun()`'s try/catch already handles correctly.
    - **Follow-up open**: `CELIGO_API_TOKEN` still needs to be added to GitHub secrets, then a real or manual run to confirm the flow actually fires and completes in Celigo.

## Platform quirks discovered along the way (useful if this ever breaks)

- monday.com's GraphQL API flatly cannot read/filter `lookup` (mirror) column types - not a reliability quirk, a hard "not supported" error.
- NetSuite's SuiteQL metadata-catalog endpoint (`/services/rest/query/v1/suiteql/metadata-catalog/...`) 500s for `salesorder`, `item`, and `transaction` record types due to unrelated dangling custom field references (`custbody_nu_shipping_calc_error`, `custitem_shinesty_forecast_end_date`) somewhere in the account's customization. Worth a NetSuite admin cleaning up eventually; the record-level metadata endpoint (`ns_getRecordTypeMetadata` equivalent, REST record API) works fine and was used instead to confirm field names.
- The standard `class` field can't be referenced bare in SuiteQL in this account (parser errors) - `cseg_order_class` works fine. To resolve a custom segment's display label from its internal ID in SuiteQL, use `BUILTIN.DF(field_name)` - the segment's own table name isn't queryable directly.
- `quantityFulfilled` on sales order lines: exists on the record, but explicitly `NOT_EXPOSED - Not available for channel SEARCH`. Use the `PreviousTransactionLineLink` / `ShipRcpt` approach instead.
- `salesrep` (on salesorder) and any field on `customer` error out completely via bulk SuiteQL (generic "unexpected SuiteScript error"), but read fine via a single-record REST fetch (`/services/rest/record/v1/...`). The script uses SuiteQL only for the order/line matching query, then per-matched-order record fetches for rep resolution.
- `transactionline.quantity` is stored **negative** for outbound transactions (Sales Orders, Item Fulfillments) per NetSuite's internal sign convention - always `ABS()` it.
- NetSuite's REST record API has no generic `item` endpoint - `/record/v1/item/{id}` 404s with `"Record type 'item' does not exist."`. Each item subtype needs its own endpoint name (e.g. `inventoryitem` for InvtPart). The script maps `item.itemtype` (pulled in the main SuiteQL query) to the right endpoint name for the pulse-comment item lookups, defaulting to `inventoryitem` since that's what all Wholesale-relevant items have been so far.
- The custom "Order Class" segment field needed its own role-level permission grant beyond normal Transaction/Item access before the TBA integration role could query it: Setup > Users/Roles > Manage Roles > [role] > Permissions > **Custom Record** category needed an "Order Class" entry (View). Separately, and less obviously, the SuiteQL REST endpoint (`/query/v1/suiteql`) also required the role to have **SuiteAnalytics Workbook** permission (found under the **Reports** permission category) - without it, every SuiteQL call 400s with a generic `"Your current role does not have permission to perform this action"` regardless of which table/field is referenced. Both were missing on Shelly's TBA integration role and had to be added before the first real query succeeded.
- monday.com's `Mutation.create_update` field requires the `updates:write` OAuth scope on the app. Editing an app's scopes on developer.monday.com doesn't retroactively upgrade a token issued under an older/draft scope set - the fix that finally worked was deleting the app entirely and creating a new one with the correct scopes from the start, then doing a completely fresh authorize flow. If this error (`"Unauthorized to load field 'Mutation.create_update', Reason: missing required scopes."`) ever comes back, check the app's scopes first, but don't assume adding a missing scope to an existing app and re-authorizing is enough - it wasn't, for reasons not fully pinned down.
- **"Option B" for feature 3's Monday columns** (2026-08-08): the idempotency checkbox and re-trigger button for the imagery-export feature were first created directly on Wholesale WIP, then moved to WIP2027 instead. Reason: WIP2027 had no Connect-Boards column pointing back to Wholesale WIP (only the reverse link exists, `board_relation_mm5z9qmh`), so a native "button pressed on WIP2027 -> change column on Wholesale WIP" automation wasn't available without adding a whole new board-relation pairing. Since WIP2027 is also where the images actually live/get edited, both pieces were kept there instead: the button->uncheck-checkbox automation is a plain same-board automation, and the script resolves the linked WIP2027 item via Wholesale WIP's existing `board_relation_mm5z9qmh` and reads/writes WIP2027's own checkbox directly (a normal column read, not a mirror, so no API limitation). A read-only mirror of that checkbox (`lookup_mm613cyz`) was added back onto Wholesale WIP purely for human visibility - like all mirror columns on this account it is NOT readable via the API, so the script never reads it.
- monday's file-type column raw `value` is a JSON string shaped like `{"files":[{"name":"...", "assetId":123, "isImage":"true", "fileType":"ASSET", "createdAt":..., "createdBy":"..."}]}` - confirmed live against WIP2027's `files2__1` on both a single-file item and a real 2-file item (SHN-3232). The array order matches upload order (ascending `createdAt`), which is what feature 3 uses as the export sequence. Asset IDs from that JSON are resolved to a downloadable URL via the root-level `assets(ids: [...])` query, which returns a `public_url` (a presigned S3 link valid ~1 hour - fine since it's downloaded immediately in the same run) plus `file_extension` (returned WITH a leading dot, e.g. `".png"`).
- monday's file-upload mutations (`add_file_to_update`, `add_file_to_column`, etc.) can't be sent as normal JSON GraphQL requests - they require a multipart/form-data POST to `https://api.monday.com/v2/file` with the mutation as a `query` form field and the binary as a separate form field (e.g. `variables[file]`) referenced by name inside that mutation string. Node 20's built-in `FormData`/`Blob` make this possible with zero extra npm dependencies (see `lib/monday.js` `mondayUploadFile()`).
- Shelly's Dropbox account has **two** folders literally named "NuOrder Imagery" - the real one (`/NuOrder Imagery`, a top-level shared folder) and an unrelated leftover (`/Apps/nuorder-imagery-netsuite-sync/NuOrder Imagery`, nested under what looks like an app-scoped folder from an earlier, separate attempt at this same integration). Confirmed which one was correct by asking Shelly directly, since resolving her original share link's exact path via the Dropbox API would have required adding a `sharing.read` scope to the app - which, like the Monday OAuth scope issue above, likely would have meant redoing the whole authorize flow. `DROPBOX_IMAGERY_FOLDER` in `run.js` is deliberately the plain top-level path.
- NetSuite's REST record API only returns a transaction's sublist detail (item lines, with fields like `isClosed` and `lineUniqueKey`) when the request includes `?expandSubResources=true` - without it, sublists come back as link-only stubs. Confirmed live via `GET /record/v1/salesorder/{id}?expandSubResources=true` against a real order (MSO-4061): returns `item.items[]`, each shaped like `{ item: { id, refName }, itemType, line, lineUniqueKey, isClosed, quantity, ... }`.
